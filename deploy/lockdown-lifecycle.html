Build initialize() for this Safe

One-shot per Safe. The install transaction atomically wires the three slots and initializes the baseline. Additional signers, timelock activation, and bypassers should be configured later as separate, independently reviewed Safe transactions.

At least one recovery owner is required (else RecoveryOwners_EmptyAllowlist). Use a cold backup, not the Safe and not a daily owner. The runbook recommends at least two distinct backups. A Safe with zero signers is installed but dormant (cannot panic).
PasswordVerifier is a one-time-password path, not a secret-preserving path. The commitment is public and the cleartext is revealed in RPC/mempool calldata at trigger time. Disclosure after a successful trigger is harmless because that identity is permanently burnt; disclosure before a successful burn lets anyone submit the same panic trigger. A failed/reverted attempt can reveal the password while leaving the identity live. Use unique high-entropy material per Safe and chain, never reuse it, and prefer private submission.

Preflight & install guards (atomic)

Installing the wrong guard can permanently block the Safe. This panel refuses to build install JSON unless the read-only preflight passes: Safe v1.5.0, Safe masterCopy is the canonical singleton, the Lockdown singleton, MultiSendCallOnly and LockdownFallbackHandler codehashes match the expected (pinned) hashes, and the singleton advertises both guard interfaces. The generated batch runs setGuard + setModuleGuard + setFallbackHandler + initialize in one Safe transaction so no asymmetric / uninitialised intermediate state is ever observable (anti T-INSTALL-1).

Verified rollback to the pre-install slot configuration

This restores the Safe's transaction guard, module guard, and fallback handler slots; it cannot erase Safe nonces/events or Lockdown's persistent per-Safe config, burnt identities, incidents, or tickets. Capture and download the snapshot before signing the install. Restoration is staged because an unknown previous guard must be installed last. The checksum detects accidental corruption; it does not authenticate an untrusted snapshot. Store the exported file with the installation evidence and independently verify every restore address/codehash.

Verifiers & panic signers

Register explicit bytes panic-signer identities (ecdsa = the 20-byte address itself; password/webauthn = verifier || key). Before a real trigger, verify the signature locally in step 7 (the signature never leaves this browser); identities that cannot be checked locally are covered by the off-contract Foundry drill script/DrillSigner.s.sol run against a local fork.

Password scheme: this is a one-time-password path. The commitment is public; at trigger time the cleartext is exposed over RPC and the public mempool. After a successful trigger the identity is permanently burnt, but a failed/reverted attempt can leak the password while it remains live, and anyone who sees it first can submit the same trigger. Use unique per-Safe, per-chain, >= 80-bit material, never reuse it, and prefer private submission. WebAuthn: register the 64-byte P-256 public key; the passkey signs the EIP-712 digest as the challenge (mempool-safe, replay-bound).

6

Timelock (anti-coercion lever, v1.0.0)

With timelockDelay == 0 the Safe has no coercion resistance: a quorum can remove the guard or disarm signers in a single transaction (INV-LIVE-1). Turning the timelock on (0→N) is free and immediate; every later change - including turning it back to 0 - must itself be scheduled and wait timelockDelay. Also note (T-LIVE-2): the effective coercion window is min(timelockDelay, lockdownDuration + resumeDelay), so do not set a short lockdown duration against a long timelock.

7

Trigger lockdown (EIP-712 panic flow)

Single-use: a successful trigger burns the signer entry and permanently retires that bytes identity. The whole Safe freezes for lockdownDuration + resumeDelay. Always verify the signature locally first.
Password trigger: the cleartext is exposed to the RPC provider and mempool. This is acceptable only as a one-time password: successful execution burns it permanently. If submission fails or reverts, assume the password leaked while still live and replace it before relying on it again. A mempool observer may front-run the same trigger; the expected security outcome is still lockdown, but submit privately when possible.

Signature

ECDSA: the burner key signs the raw digest (no personal_sign prefix); a connected wallet signs the EIP-712 typed data (eth_signTypedData_v4, clear-signed). WebAuthn: the passkey signs the digest as its challenge. Password: the cleartext IS the signature (leaks over the mempool at submit). Signatures are checked locally only: a valid signature is a live trigger credential, so never send it to an RPC (no eth_call drill).

Recovery operations

Recovery JSON is for the post-lockdown window only (state = Recovering). The whitelist is narrow: empty nonce burn, swapOwner to a pre-registered backup, disableModule, and removeLockdownSigner. The Safe returns to Normal automatically after lockdownUntil + resumeDelay; no resume transaction exists. All refund fields (safeTxGas/baseGas/gasPrice/gasToken/refundReceiver) MUST be zero.
